# Nebula Agent · Deployment & Startup Guide

> [简体中文](部署说明.md) | **English**

This file explains how to deploy the standalone edition of Nebula Agent on a new machine, and how to
start it day-to-day, switch models, and add external cloud models.

---

## 1. Overall architecture (understand this before deploying)

The standalone edition has two layers that talk to each other over local HTTP:

| Layer | Process | Port | Role | Where it comes from |
|---|---|---|---|---|
| Inference engine | `run-swift-iq3_*.bat` → Strata `server.py --engine strata` | **8080** | The actual compute for the local iq3 model (s / xxs), including vision | `E:\Program Files\Strata-main` |
| Standalone gateway | `run_standalone.bat` → `Nebula-agent/runtime/gateway.py` | **8099** | Web UI + 36 tools (MCP) + the local agent loop; forwards LLM calls to 8080 | `Nebula Baize / Nebula-agent` |

Key facts:
- The gateway's **frontend, tools, and the gateway program itself all live inside `Nebula-agent/`**, unrelated to Strata's `serve/`.
- The gateway only forwards "LLM chat requests" to 8080; tools (files, shell, web, memory, etc.) run locally.
- **The launcher only handles 8099 (as of 2026-11-22):** double-clicking `星云白泽.bat` starts only the gateway watchdog, and 8099 is brought up by it on demand; it **no longer auto-starts the 8080 inference engine**. For local iq3 inference, double-click `run-swift-iq3_*.bat` separately (or just use a cloud model, in which case 8080 is not needed at all).
- **The parasitic edition is retired (2026-10):** there is no longer a "parasitic frontend entry" mode; the single authoritative frontend source is `Nebula-agent/serve/web/`. `Strata-main` is kept only as the local-model inference engine.
- **`E:\Program Files\Strata-main` must not be deleted:** the local iq3 inference binary (`strata.exe`) + weights (`Strata-data\`) live there. Only by switching to a pure cloud model can you stop depending on it entirely.

## 2. Deployment steps on a new machine

> Prerequisite: copy the entire `Nebula Baize` project directory to the new machine (preferably at a path with no Chinese characters or spaces, or keep the current structure). `Strata-main` must also be copied over (or installed via the official Strata process).

**Only two steps:**

### Step 1: double-click `setup.bat` (environment prep, one-time)

It does the following automatically, with no manual path editing:
1. **Detect an existing Python (≥3.10)**: first the `py -3` launcher → `python` on PATH → scanning common install dirs. **If found, it is used directly and the download is skipped.**
2. **Download only as a fallback**: an online download + silent install of Python 3.14 (user-level, added to PATH). This happens only when the machine has no usable ≥3.10 Python at all. The exact patch version is **resolved dynamically** — the script first queries `endoflife.date` for the latest 3.14 patch (falling back to `3.14.10` if unavailable), so it **no longer hardcodes a version that could be removed from python.org and 404**.
3. **Create a project-local virtualenv**: `Nebula-agent\.venv` (fully decoupled from the user name and the Python install path).
4. **Rewrite config**: change the Python path in the 2 files below to `Nebula-agent\.venv\Scripts\python.exe` (no more machine-specific hardcoded paths like `C:\Users\sk\...`):
   - `Nebula-agent/config/mcp_servers.json` (the command of the 8 MCP tools)
   - `Nebula-agent/run_standalone.bat`
5. **Verify**: load all 8 tools + the gateway/executor using the venv's Python and confirm no import errors.

> Idempotent: safe to re-run. Paths already pointing at the venv are not rewritten again.

### Step 2: double-click `星云白泽.bat` (start the service)

It does exactly one thing (single-point startup, as of 2026-11-22): **start the gateway watchdog** (`Nebula-agent\gw_watchdog.bat`).

1. After invoking the watchdog the launcher closes its window immediately (no pause); the watchdog stays resident in the background in its own minimized window.
2. The watchdog probes 127.0.0.1:8099 every 5 seconds; **when it is not listening and there is no `.gw_stop.flag`, it automatically launches `run_standalone.bat` (with a crash-restart self-heal loop)** to serve 8099. So the launcher does not start the gateway itself — it delegates that to the watchdog, removing duplicated startup logic.
3. The watchdog has a **single-instance guard** and a **double-instance guard**: repeated double-clicks are skipped automatically; if a gateway process is already running (even if momentarily not listening), it also skips to avoid a double instance.

Done. Within a few seconds 8099 is brought up by the watchdog; open `http://127.0.0.1:8099` in a browser to chat.

> This launcher **no longer auto-starts the 8080 inference engine**: your machine may use an online API or another local service and may not need 8080. For local iq3 inference, double-click `E:\Program Files\Strata-main\run-swift-iq3_s.bat` separately (see "3. Day-to-day start / stop" below).

## 3. Day-to-day start / stop

- **Start**: double-click `星云白泽.bat` (recommended; it starts only the watchdog, which brings 8099 up and keeps self-healing it).
- **Local inference engine 8080 (optional, start it yourself)**: double-click `E:\Program Files\Strata-main\run-swift-iq3_s.bat`. When using only cloud models, it is entirely unnecessary.
- **Manually start just the gateway (without the watchdog, also supported)**: double-click `Nebula-agent\run_standalone.bat`.
- **Stop**: to stop the gateway and keep it from being auto-relaunched, first create a `.gw_stop.flag` under `Nebula-agent\` for a soft stop (the watchdog exits when it sees it), then close the gateway/watchdog windows; or kill the corresponding processes.

> It does not auto-start after a machine reboot; you must double-click `星云白泽.bat` again.

## 4. Switching the local model (s / xxs, pick one)

The two models **share port 8080 and run mutually exclusively** (the RTX 2080 Ti's 22GB VRAM is filled by a single engine and cannot hold both at once).

- **Option A (pick the matching engine launch file, recommended)**: the launcher no longer manages 8080, so switching models = stop the current engine, then double-click the matching `run-swift-iq3_s.bat` or `run-swift-iq3_xxs.bat`; the two share 8080 and are mutually exclusive, so you must stop the running one first, otherwise the new engine can't come up and you'll connect to the old one.
- **Option B (manual)**: stop the current engine → double-click `run-swift-iq3_s.bat` or `run-swift-iq3_xxs.bat` → in the web UI's model switcher, select the corresponding model (`iq3-s` is the default; `iq3-xxs` must be switched manually).

Both launch files use `--port` **8080** (after the Strata upgrade, 8080 is the default; the model is chosen via the two-file pick), and `config/models.json` also points `iq3-xxs`'s `base_url` at 8080, so the two are consistent.

## 5. Adding an external cloud API model

At the bottom of the web chat, click "Switch model / Settings" → **Add custom model** (choose "External endpoint / OpenAI-compatible"):
- **Endpoint**: fill in up to `/v1`, e.g. `https://api.openai.com/v1` or your proxy address;
- **API Key**: paste it;
- **Model name**: the real id from the provider (e.g. `gpt-4o`, `qwen2.5:14b`);
- Click **Test connection** first to probe, then **Save**.

After saving it is written to `Nebula-agent/config/models.json` (the key is stored only server-side and never returned to the page), **effective immediately, no gateway restart needed**.

Mechanism: external models are written as `kind:"custom"`; the gateway runs the agent loop with your 36 local tools and only sends the LLM requests to the external endpoint — so a cloud model can also call local file/shell tools. Note: for a cloud model to use tools, that model itself must support function-calling.

## 6. Common troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Chat keeps 502 / no reply (when a local model is selected) | The local 8080 engine isn't running (the launcher no longer starts it automatically), or the wrong model is selected | Double-click `run-swift-iq3_s.bat` (or the matching model) separately; in the UI confirm the selected model matches the running engine |
| All tools/skills unavailable (MCP not found) | `setup.bat` was never run, or config still points at the old machine's paths | Re-run `setup.bat` on the new machine to regenerate the venv and rewrite paths |
| `setup.bat` errors "could not obtain a Python" | Offline and no Python on the machine, and the download fallback failed | Install Python 3.10+ manually (check Add to PATH), then re-run `setup.bat` |
| Port in use | Last run wasn't shut down cleanly | Just kill the process on that port; the watchdog detects an already-running gateway and skips, so it won't start a duplicate |
| Standalone edition breaks after a Strata upgrade | Rare; an upgrade rewriting `serve/` doesn't affect our project, but confirm the engine launch args are unchanged | Confirm `run-swift-iq3_*.bat` still carries `--mcp-config`; re-run `星云白泽.bat` |

## 7. File inventory (project root)

| File / Directory | Role |
|---|---|
| `setup.bat` | New-machine environment prep entry (detect/install Python, create venv, rewrite config) |
| `Nebula-agent\gw_watchdog.bat` | Gateway watchdog (this is what the launcher actually starts after a double-click; it auto-launches run_standalone when 8099 is down) |
| `星云白泽.bat` | One-click start (starts only the gateway watchdog; 8099 is brought up on demand, no longer auto-starts 8080) |
| `Nebula-agent\` | The standalone body: gateway (`runtime/`), tools (`servers/`), frontend (`serve/web/`), config (`config/`) |
| `Nebula-agent\setup_env.py` | Helper script invoked by `setup.bat` (create venv + rewrite config + verify) |
| `Nebula-agent\config\mcp_servers.json` | Launch definitions for the 8 MCP tools |
| `Nebula-agent\config\models.json` | Model list (local s/xxs + custom cloud models) |
| `Nebula-agent\.venv\` | Project-local Python virtual environment (generated by `setup.bat`) |

> `E:\Program Files\Strata-main\` is a third-party inference engine, installed/maintained separately; it is not part of this project directory.

## 8. Visual verification (how to confirm pixels after changing the frontend)

- The authoritative frontend `Nebula-agent/serve/web/index.html` loads styles via a relative `web/` path, which only resolves when loaded through the gateway (8099). **Opening that HTML directly with `file://` loads none of the CSS** — the Nebula core renders black, text has no color, sub-line color separation is lost; this is a "styles not loaded" illusion, not a failed change.
- Therefore visual verification **must go through the running service URL** (`http://127.0.0.1:8099/`), using a headless browser (the screenshot in `servers/browser_server.py`) to capture pixels; you cannot conclude from a `file://` open.
- Verify the light theme (`data-theme="light"`) separately once, to confirm red/green/gold-yellow do not bleed on a light background (each light color has a one-shade-darker override).
